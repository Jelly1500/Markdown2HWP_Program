# 버그 리포트

## 어떤 버그인가요?

> 마크다운 문서에서 복잡한 중첩 목록을 사용할 때, 숫자 목록(1, 2, 3)은 정상적으로 변환되지만 **알파벳 소문자(a, b, c)**, **로마 숫자(i, ii, iii)**, **괄호형 목록((1), (2), (a), (b))**, **대문자 알파벳(A, B, C)** 등의 다양한 목록 스타일이 한글 문서 변환 시 적용되지 않아 모든 목록이 동일한 숫자 스타일로 표시되는 문제가 발생합니다. 이는 법령, 지침, 규정 등 공식 문서에서 계층적 구조를 명확히 표현하는 데 필수적인 기능이 제대로 작동하지 않는 문제입니다.

<br><br>

## 어떤 상황에서 겪으셨나요?

1. 실행 환경: Windows 10, Python 가상환경
2. 테스트를 수행한 마크다운 문서: 공공데이터 개방 및 이용 활성화 지침 (개정안)
3. 테스트한 템플릿: 
   - template_ex_01.hml
   - template_ex_02.hml
   - template_ex_03.hml
   - 새템플릿.hml
   - 템플릿문서.hml
   - 템플릿문서1.hml

테스트한 마크다운 텍스트:
```markdown
# 공공데이터 개방 및 이용 활성화 지침 (개정안)

## 제1조 (목적)
본 지침은 공공기관이 보유·관리하는 데이터의 개방을 확대하고, 국민의 데이터 이용을 활성화하여 새로운 가치 창출 및 공공의 이익 증진에 기여함을 목적으로 한다.

## 제2조 (용어의 정의)
1.  "공공데이터"란 데이터베이스, 전자화된 파일 등 공공기관이 법령 등에서 정하는 목적을 위하여 생성 또는 취득하여 관리하고 있는 광(光) 또는 전자적 방식으로 처리된 자료 또는 정보를 말한다.
    a.  "기계 판독이 가능한 형태"라 함은 소프트웨어로 데이터의 개별 내용과 내부 구조를 확인하거나 수정, 변환, 추출 등 가공할 수 있는 상태를 의미한다.
        i.  예시: CSV, JSON, XML 등
        ii. 비예시: PDF (이미지 형태), HWP (내용 복사가 어려운 경우)
    b.  "개방"이라 함은 공공데이터를 이용자가 정보통신망을 통하여 접근하거나 재활용할 수 있도록 제공하는 것을 말한다.
2.  "제공대상 데이터"란 법 제17조제1항에 따라 개방 대상이 되는 공공데이터를 의미한다.

## 제3조 (개방 원칙)
공공데이터는 다음 각 호의 원칙에 따라 제공되어야 한다.
A.  적극적 개방의 원칙
    1.  공공기관은 보유·관리하는 데이터를 최대한 개방하여야 한다.
        a.  비공개 대상정보를 제외한 모든 데이터는 원칙적으로 개방 대상이다.
            i.  국가안보, 사생활 침해 등 법률에 따른 비공개 사유 명확히 제시
    2.  국민이 필요로 하는 데이터를 우선적으로 발굴하여 개방하여야 한다.
B.  이용자 중심의 원칙
    1.  개방되는 데이터는 이용자가 쉽게 접근하고 활용할 수 있는 형태로 제공되어야 한다.
        a.  오픈 포맷(Open Format) 및 기계 판독이 가능한 형태로 제공
            i.  표준 API 제공 노력
            (1) RESTful API 권장
            (a) 인증 방식: OAuth 2.0 기반
            (b) 데이터 형식: JSON 우선 고려
            ii. 대용량 데이터의 경우 파일 다운로드 방식 병행
        b.  데이터 최신성 유지 및 주기적 갱신
    2.  데이터 활용을 위한 교육 및 기술 지원을 강화한다.

## 제4조 (지침의 적용)
본 지침은 모든 중앙행정기관 및 지방자치단체, 공공기관에 적용된다.
```

## 어떤 과정에서 버그가 발생했나요?

1. 위 마크다운 텍스트를 파일로 저장
2. 각각의 템플릿으로 변환 테스트 수행
3. 변환 결과 확인:
   - 모든 템플릿에서 동일한 문제 발생:
     * 변환 자체는 성공하여 HWP 파일이 생성됨
     * 하지만 다양한 목록 스타일이 적용되지 않아 다음과 같은 문제 발생:
       - 숫자 목록(1, 2, 3)은 정상적으로 표시됨
       - 알파벳 소문자 목록(a, b, c)이 숫자로 변환되거나 무시됨
       - 로마 숫자 목록(i, ii, iii)이 숫자로 변환되거나 무시됨
       - 괄호형 목록((1), (2), (a), (b))의 괄호가 무시되고 일반 숫자로 표시됨
       - 대문자 알파벳 목록(A, B, C)이 숫자로 변환되거나 무시됨

### 구체적인 문제 상황:
1. **기대되는 결과:**
   - 1단계: 숫자 목록 (1, 2, 3...)
   - 2단계: 알파벳 소문자 (a, b, c...)
   - 3단계: 로마 숫자 소문자 (i, ii, iii...)
   - 4단계: 괄호형 숫자 ((1), (2), (3)...)
   - 5단계: 괄호형 알파벳 ((a), (b), (c)...)
   - 대문자 알파벳 (A, B, C...)도 독립적으로 지원

2. **실제 발생하는 결과:**
   - 모든 목록이 동일한 숫자 스타일(1, 2, 3...)로 표시됨
   - 계층적 구조의 시각적 구분이 불가능
   - 법령이나 지침의 조항 구분이 모호해짐
   - 공식 문서의 표준 형식에 맞지 않는 결과물 생성

### 영향을 받는 목록 스타일:
1. **알파벳 소문자 목록 (a, b, c...)**
   - 마크다운: `a.`, `b.`, `c.`
   - 결과: 숫자 목록으로 변환되거나 스타일 무시

2. **로마 숫자 소문자 목록 (i, ii, iii...)**
   - 마크다운: `i.`, `ii.`, `iii.`
   - 결과: 숫자 목록으로 변환되거나 스타일 무시

3. **괄호형 숫자 목록 ((1), (2), (3)...)**
   - 마크다운: `(1)`, `(2)`, `(3)`
   - 결과: 괄호가 제거되고 일반 숫자 목록으로 표시

4. **괄호형 알파벳 목록 ((a), (b), (c)...)**
   - 마크다운: `(a)`, `(b)`, `(c)`
   - 결과: 숫자 목록으로 변환되거나 완전히 무시

5. **대문자 알파벳 목록 (A, B, C...)**
   - 마크다운: `A.`, `B.`, `C.`
   - 결과: 숫자 목록으로 변환되거나 스타일 무시

6. **로마 숫자 대문자 목록 (I, II, III...)**
   - 마크다운: `I.`, `II.`, `III.`
   - 결과: 숫자 목록으로 변환되거나 스타일 무시

### 특히 문제가 되는 상황:
1. **법령 및 규정 문서**
   - 조, 항, 호의 구분에 다양한 목록 스타일이 필수적임
   - 예: 제1조 → 1. → 가. → (1) → (가) 형태의 계층 구조

2. **정책 지침 문서**
   - 단계별 세부 사항을 구분하기 위한 다양한 목록 스타일 필요
   - 현재는 모든 단계가 동일한 스타일로 표시되어 혼란 야기

3. **회의록 및 보고서**
   - 안건별, 세부 사항별 구분을 위한 다양한 목록 표기 필요
   - 계층적 정보 구조 표현 불가

### 예상되는 원인:
1. 마크다운 파서에서 숫자 목록 외의 다른 목록 스타일 인식 기능 부재
2. HWPML 변환 과정에서 다양한 목록 스타일에 해당하는 서식 정의 누락
3. 목록 타입별 렌더링 로직이 숫자 목록만 구현되어 있음
4. 한글 문서의 다양한 목록 스타일 매핑 테이블 부재
5. 중첩된 목록에서 각 레벨별 스타일 자동 적용 기능 누락

### 심각도:
- 🐛 중간 (Medium)
- 📝 서식 미지원
- 변환은 성공하지만 공식 문서에서 중요한 계층적 구조 표현이 불가능
- 법령, 지침, 규정 등 공식 문서의 표준 형식에 맞지 않는 결과물 생성
- 모든 템플릿에서 동일한 문제가 발생하여 대체 방안 없음
- 문서의 전문성과 가독성이 저하되지만 내용 자체는 손실되지 않음
- 수동으로 한글 문서에서 목록 스타일을 변경하여 부분적 해결 가능

### 해결 방안 제안:
1. 마크다운 파서에 다양한 목록 스타일 인식 기능 추가
2. HWPML 템플릿에 각 목록 스타일별 서식 정의 추가
3. 목록 레벨별 자동 스타일 적용 규칙 구현
4. 한국의 공문서 표준에 맞는 목록 스타일 매핑 테이블 작성
5. 사용자가 목록 스타일을 수동으로 지정할 수 있는 옵션 제공
